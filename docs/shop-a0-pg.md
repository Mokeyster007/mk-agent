# A0-PG：真实 PostgreSQL 回归验收

> 目的：A0 此前只在 H2（`MODE=PostgreSQL`）上验证过。本文记录在**真实 PostgreSQL 16**
> 上重跑 A / B / C / D / E 五个场景的接线方式、实测证据、发现的问题与剩余限制。
> 不涉及 A1，不改商城业务逻辑。

## 2. 环境与连库自证

```
Docker Engine   29.4.3（Docker Desktop，linux 容器）
Docker 端点     npipe:////./pipe/dockerDesktopLinuxEngine
镜像            pgvector/pgvector:pg16      ← 与仓库 docker-compose.yml 一致
服务端版本      PostgreSQL 16.15 (Debian 16.15-1.pgdg12+2) on x86_64-pc-linux-gnu
server_version_num  160015
默认隔离级别    read committed
```

镜像标签固定主版本 16，不用 `latest`；真实版本以 `SELECT version()` 为准，
不靠标签推断（`ShopPostgresAcceptanceTest#databaseIsRealPostgres` 会断言
`version().startsWith("PostgreSQL 16")`）。

**连库自证**放在 `@BeforeEach`，而不是只做一个用例：

```java
assertEquals("PostgreSQL", dataSource.getConnection().getMetaData().getDatabaseProductName(), ...);
```

一旦连接被回落到 `application-test.yml` 里的 H2，**每个**用例都会立刻失败，
不会出现"部分用例在 H2 上通过"的假绿。

## 3. 测试接线

### 3.1 为什么没有用 Testcontainers

先按要求试了 Testcontainers，失败，并且定位到了明确的根因：

| 尝试 | 结果 |
| --- | --- |
| `@ServiceConnection` + 静态容器（Boot 管理的 1.20.6） | `InvalidPathException: Illegal char <?>` |
| 清理 fork 的 PATH（去掉非 ASCII 条目） | 该异常消失，转为 `Could not find a valid Docker environment` |
| `-Ddocker.host=npipe:////./pipe/dockerDesktopLinuxEngine` | 端点正确，仍 `BadRequestException (Status 400)` |
| 升级 Testcontainers 到 1.21.3 | 同一个 400 |

用 CLI 复现同一条请求，确认不是端点/权限问题，而是 **API 版本**：

```
docker -H npipe:////./pipe/dockerDesktopLinuxEngine info        → 29.4.3（正常）
DOCKER_API_VERSION=1.32 docker ... info                        → 400 Bad Request（无错误消息）
DOCKER_API_VERSION=1.44 docker ... info                        → 29.4.3（正常）
docker version --format '{{.Server.MinAPIVersion}}'            → 1.40
```

结论：Docker Engine 29 的**最低 API 是 1.40**，Testcontainers 1.20.6 / 1.21.3
内置客户端固定使用 **1.32**，且没有暴露"指定 API 版本"的开关
（`DOCKER_API_VERSION` 对它无效）。这是版本兼容性问题，不是配置问题。

顺带发现的第二个环境缺陷：本机 PATH 里存在**无法被 JVM 当前
`sun.jnu.encoding`(GBK) 编码**的目录（实测 `C:\Users\????\...`）。
Testcontainers 在枚举 Docker 端点时会遍历 PATH，`Paths.get()` 直接抛
`InvalidPathException`。`sun.jnu.encoding` 无法用 `-D` 覆盖，只能给 fork 换一组 PATH。

### 3.2 实际采用的方案

**Docker CLI 起一次性容器 + `@DynamicPropertySource` 接线**，隔离性与可清理性与
Testcontainers 一致，只是少了自动发现：

```
docker run -d --rm --name mk-agent-a0pg-<随机> --label mkagent.a0pg=1 \
  -p 127.0.0.1::5432 \
  -e POSTGRES_USER=... -e POSTGRES_PASSWORD=<随机> -e POSTGRES_DB=mk_agent_a0pg \
  pgvector/pgvector:pg16
```

- 端口由 Docker 随机分配（`docker port` 回读），不与既有 `mk-agent-postgres`（5432）冲突；
- 口令随机生成，不落盘、不打印；
- 轮询到**能真正建立 JDBC 连接**才继续（容器起来 ≠ PostgreSQL 可接受连接）；
- JVM 退出时 shutdown hook 执行 `docker rm -f`，实测无残留（`docker ps -aq --filter label=mkagent.a0pg` 为空）。

连接通过 `@DynamicPropertySource` 注入，并**显式覆盖驱动**：

```java
registry.add("spring.datasource.url", () -> "jdbc:postgresql://127.0.0.1:" + port + "/" + db);
registry.add("spring.datasource.driver-class-name", () -> "org.postgresql.Driver");
```

> 只改 url 不改驱动会踩坑：`application-test.yml` 写死了 `org.h2.Driver`，
> Spring 会拿 H2 驱动去连 PG URL。

### 3.3 schema 与模型隔离

- **空库直接用项目自己的初始化入口**：`spring.sql.init.mode=always` +
  `schema-locations=classpath:db/schema.sql`，没有为测试另写一份 DDL。
  这同时验证了 `schema.sql` 本身在真实 PG 上可执行（`COMMENT ON`、
  `GENERATED BY DEFAULT AS IDENTITY`、`CREATE UNIQUE INDEX IF NOT EXISTS` 等）。
- **不调用真实 AI**：沿用 `application-test.yml` 的自动配置排除项
  （DashScope chat/agent/embedding/audio/image/rerank、MCP、pgvector），
  上下文里没有可用的真实模型。
- **复用 A0 的真实 HTTP 测试方式**：`RANDOM_PORT` + `ShopApiClient`
  （`java.net.http.HttpClient`），每个并发请求各自开事务、各自拿连接。
  不用 MockMvc——它共用一个线程和事务，并发场景测出来的"通过"是假的。

### 3.4 分组与命令

`@Tag("pg")`，pom 的 `mkagent.test.excluded-groups` 默认含 `pg`，所以默认构建不跑。

```bash
# Windows（本机）：-Ppg 会把 fork 的 PATH 收窄到系统目录 + Docker CLI 目录
./mvnw -Ppg test -Dtest='ShopPostgres*'

# Unix：不需要 PATH 覆盖
./mvnw test -Dmkagent.test.excluded-groups=live -Dgroups=pg -Dtest='ShopPostgres*'
```

`-Ppg` 只做两件事：把 `excludedGroups` 调成 `live`，以及覆盖 fork 的 PATH
（原因见 3.1 的第二个环境缺陷）。它**不影响默认构建**。

用例确实被执行（不是零用例、不是跳过）：

```
[INFO] Tests run: 8, Failures: 0, Errors: 0, Skipped: 0 -- ShopPostgresAcceptanceTest
[INFO] Tests run: 5, Failures: 0, Errors: 0, Skipped: 0 -- ShopPostgresIdentityDisabledTest
[INFO] Tests run: 13, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
```

## 4. 五个场景的实测结果

### A. 主流程（初始库存 10，买 2 件）

| 步骤 | 库存 | 订单状态 | 流水条数 | 响应 |
| --- | --- | --- | --- | --- |
| 下单 | **10** | `PENDING_SHIPMENT` | 0 | 201 |
| 发货 | **8** | `SHIPPED` | **1**（`-2` / `OUTBOUND_SHIPMENT`，`order_item_id` 非空） | 200 `applied=true` |
| 签收 | **8** | `SIGNED` | 1 | 200 `applied=true` |

`shop_order.signed_at` 已持久化（独立查询非空）；重新 `GET /shop/orders/{no}`
读到 `SIGNED` + `signedAt` + 1 条流水——证明是库里的状态，不是内存态。

### B. 同一订单重复发货

| 子场景 | 两个请求的结果 | 库存 | 流水 |
| --- | --- | --- | --- |
| B1 顺序重试 | 第一次 `applied=true`，第二次 `applied=false` | 8 | 1 |
| B2 并发（闸门同时放行） | `[200 applied=false, 200 applied=true]` | 8 | 1 |
| B3 受控锁等待 | 外部事务持有 `FOR UPDATE` 时，发货请求**阻塞 ≥500ms**；释放后 **27ms** 完成 | 8 | 1 |

### C. 不同订单争抢同一 SKU（库存 3，两单各 2）

```
[status=200 applied=true, status=409 code=INSUFFICIENT_STOCK applied=false]
最终库存=1
```

- 恰好一单成功（`SHIPPED`，1 条流水），另一单 `409 INSUFFICIENT_STOCK`；
- 失败订单仍为 `PENDING_SHIPMENT`，**0 条流水**；
- 库存 1（3 − 2），不为负。

### D. 事务回滚（在扣减之后、提交之前注入失败）

注入点：`InventoryRepository#insertMovement`（spy + `doAnswer`，**生产代码里没有故障开关**）。

```
[pg-evidence] 故障注入：事务内读到扣减后库存=8，请求 status=500；
              回滚后库存=10 流水=0 订单=PENDING_SHIPMENT
```

- `事务内读到 8` 是关键证据：说明扣减**真的发生过**，失败发生在它之后。
  这样才排除了"库存不足、根本没扣成功"被当成"回滚验证通过"。
- 移除注入后重试：200 `applied=true`，库存 8，流水 1 条——只扣一次。

### E. 权限

| 断言 | 实际结果 |
| --- | --- |
| 买家 A 读买家 B 的订单 | **404**（不是 403，避免泄露订单号真实存在） |
| 买家 A 的订单列表 | 0 条（不含 B 的单） |
| 买家调用发货 | **403 `NOT_ADMIN`**，且库存仍 10、订单仍待发货、0 流水 |
| 关闭演示身份后读私有订单（带 BUYER 头） | **403 `SHOP_IDENTITY_NOT_CONFIGURED`** |
| 关闭演示身份后读后台列表 / 库存（带 ADMIN 头） | **403 `SHOP_IDENTITY_NOT_CONFIGURED`** |
| 关闭演示身份后下单 / 发货 / 签收 | 全部 403，且库中只有夹具那一单、库存未动、流水未增 |
| 关闭演示身份后浏览商品 | **200**（公开行为不受影响） |

## 5. 并发测试是否真的安排了锁竞争

需要区分两件事，本文不把"同时发请求"说成"观测到了行锁等待"：

- **B2 / C 是屏障并发**：`CountDownLatch` 同时放行两个真实 HTTP 请求，
  每个请求独立事务。它们能证明**结果**正确（只应用一次、库存不为负），
  但"是否发生锁等待"取决于调度，不能从结果反推。
- **B3 是受控锁等待**：用一条独立连接先 `SELECT ... FOR UPDATE` 锁住订单行，
  再发发货请求，断言 500ms 后请求**仍未完成**、期间库存未变；
  释放锁后请求在 27ms 内成功。
  这才是"观测到行锁等待"的直接证据。

另外 `PostgresIdempotencyConcurrencyTest`（既有 pg 用例）已经验证过
唯一索引上的等待与 `SET LOCAL lock_timeout` 的边界行为，本组用例没有重复造。

## 6. 发现的问题

**没有发现 A0 的 PG 兼容性或事务缺陷。** 13 个用例第一次在真 PG 上跑，
除一处**测试断言写错**外全部通过：

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| `sessionReportsDisabled` 期望 `role=UNKNOWN`，实际 `BUYER` | 断言写错，不是实现错 | 改断言 |

`ShopAccessGuard.session()` 的语义是"你是谁"与"你能做什么"分开：
关闭演示身份时 `identityMode=DISABLED`、`canOrder=false`、`canOperate=false`，
但 `role` 仍如实返回该身份在 `shop_user` 里的角色。
受保护写操作在 `requireProtectedWritesEnabled()` 就 403 了，不会因为 `role` 有值而放行。
把 `role` 改成 `UNKNOWN` 反而会让排查"为什么不能下单"少一条线索，因此**不改实现**。

## 8. 剩余限制（明确未验证）

1. **Testcontainers 在本机不可用**：客户端 API 1.32 与 Docker Engine 29（最低 1.40）
   不兼容，`DOCKER_API_VERSION` 无效、升级到 1.21.3 无效。
   因此本组用例用 Docker CLI 起容器。换到 Docker 25 及以下、或 Testcontainers
   发布支持新 API 的版本后，可以改回 `@ServiceConnection`——断言部分不需要改。
2. **只在 PG 16.15 上验证**。其他主版本的锁/约束行为未测。
3. **未验证**：`SERIALIZABLE` 等其他隔离级别；PG 主备/连接池耗尽；跨库分布式事务。
4. **并发规模有限**：每个场景 2 个并发请求。不是压测，不声称吞吐或高并发稳定性。
5. **故障注入只覆盖"写流水失败"这一条路径**。"更新订单状态失败"未单独注入
   （两者都在同一事务内、同一回滚边界上，但严格说没有各自验证）。
6. 容器依赖本机 Docker Desktop；CI 上需要有可用 Docker 才能跑 `-Ppg`。

## 9. 清理

测试结束时 shutdown hook 删除容器。确认命令：

```bash
docker ps -aq --filter label=mkagent.a0pg    # 期望为空
```

若异常中断留下残留：

```bash
docker ps -aq --filter label=mkagent.a0pg | xargs -r docker rm -f
```

本组用例**不触碰**既有的 `mk-agent-postgres`（docker-compose 起的 5432 实例），
也不读写任何业务库或 demo 库。
