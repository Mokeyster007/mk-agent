# 商城售后 B3：模拟退款

> 本轮把链路补到 **「订单 → 售后申请 → 客服批准 → 仓库收货 → 模拟退款」** 的闭环。
> 一张**已批准且全部实收**的退货单可以生成**一笔**退款记录，
> 金额 = **原订单成交单价 × 累计实收**（含损坏件）。
>
> 它是**模拟**退款：不接支付平台、不产生真实资金流、不发通知。
> 退款**不动可售库存、不写第二条入库流水、不释放可退额度**。

---

## 1. 范围

| 做了 | 没做（留给后续阶段） |
| --- | --- |
| 退款接口 `POST /shop/admin/aftersale/returns/{returnNo}/refund`（后台角色守卫） | 真实支付/退款通道、对账、发票、退款回执 |
| 独立退款表 `shop_aftersale_refund`，关联退货单 | 部分退款、多次退款、按金额比例退 |
| 金额 = 成交单价 × 累计实收（整数分，溢出拒绝） | 运费/优惠券/税费的退款分摊 |
| 一张退货单最多一笔（`uk(return_id)` + 服务层 409） | 退款撤销 / 冲正 |
| 买家列表、买家详情、客服列表、客服详情、Agent 查询全部**只读**可见 | 买家侧发起退款、买家 Agent 写退款 |
| 退款与库存、流水、额度**完全解耦** | 通知（站内信 / 推送） |
| 顺带修掉 B2 最后一批收货的幂等边界（见第 5 节） | 多仓、真实认证（`X-User-Id` 仍是 demo 边界） |

A0 的发货出库、A1 的提交、B1 的批准 / 驳回、B2 的收货入库**行为未变**（回归见第 8 节）。

## 2. 业务规则

### 2.1 谁能退：已批准 + 全部实收

```
status == APPROVED                 否则 409 REFUND_NOT_ALLOWED
sum(received_qty) == quantity      否则 409 REFUND_NOT_RECEIVED
```

- **待审批**不能退：还没同意退，退什么？
- **已驳回**不能退：实物应退回买家，钱本来就不该动。
- **没收满**不能退：批准 2 件只收回 1 件时退全款，等于为一件还没回来的货付钱。
  注意判断用的是**累计实收**，不是合格件数——损坏件也算收回来了。

### 2.2 金额：成交单价 × 累计实收

```
amount_cents = 原订单行 unit_price_cents × sum(received_qty)
```

三个刻意的选择：

| 选择 | 理由 |
| --- | --- |
| 用**累计实收**，不用合格件数 | 退款退的是"买家寄回来几件"。合格与否只决定"能不能再卖"，那是 B2 的事 |
| 用**订单行成交单价**，不用退货单上的估算快照 | 成交价是这笔交易的真实价格；两者不一致说明数据被绕过业务路径改过，此时**拒绝**比按来源不明的单价退钱安全 |
| 整数分 + `Math.multiplyExact` | 复用 A1 既有的 `AfterSaleMoney.refundCents`；溢出 → 400 `REFUND_AMOUNT_OUT_OF_RANGE` |

金额**由服务端算**，接口没有金额字段：前端传不进来，也改不了。

### 2.3 一张退货单最多一笔

```sql
CONSTRAINT uk_shop_aftersale_refund_return UNIQUE (return_id)
```

唯一键是**事实来源**，服务层的"先查再插"只是让常见路径给出可解释的错误。
并发重复点击时：一个成功，另一个拿 `DuplicateKeyException`，
服务层按退货单回查赢家，翻译成 409 `REFUND_ALREADY_EXISTS` 并**带上原退款单号**。

### 2.4 退款不做什么（三条边界）

| 不动 | 为什么 |
| --- | --- |
| 可售库存 | 库存在 B2 收货时已按合格件数回补过；退款再改一次就是重复计算 |
| 入库流水 | 流水按收货记录去重（`IN:{receipt_id}`）；退款不是入库动作 |
| 可退额度 | 额度在批准时就已保留（收货也不释放）。放回去等于允许同一件商品被退第二次 |

| 方法 | 路径 | 守卫 | 说明 |
| --- | --- | --- | --- |
| POST | `/shop/admin/aftersale/returns/{returnNo}/refund` | `requireAdmin()` | 生成一笔模拟退款，201 + 退货单详情（含 `refund`） |
| GET | `/shop/aftersale/returns`、`/{returnNo}` | 买家本人 | 列表与详情带 `refund`（可为 null） |

错误码（全部是稳定码，界面按 code 分支，不解析中文）：

| HTTP | code | 含义 |
| --- | --- | --- |
| 409 | `REFUND_NOT_ALLOWED` | 不是已批准（待审批 / 已驳回） |
| 409 | `REFUND_NOT_RECEIVED` | 还没收满批准数量 |
| 409 | `REFUND_RECEIPT_QUANTITY_MISMATCH` | 累计实收**超过**批准数量（数据不一致，C1 补的，见 `docs/shop-c1.md` 第 6 节） |
| 409 | `REFUND_ALREADY_EXISTS` | 这张单已经退过（消息带原单号） |
| 409 | `REFUND_AMOUNT_MISMATCH` | 退货单单价快照与订单行不一致 |
| 400 | `REFUND_AMOUNT_OUT_OF_RANGE` | 金额溢出 |
| 403 | `NOT_ADMIN` | 买家调用退款接口 |
| 403 | `SHOP_IDENTITY_NOT_CONFIGURED` | demo 身份关闭（优先于权限判定） |
| 404 | `RETURN_NOT_FOUND` | 退货单不存在 |

**买家 Agent 没有退款写工具**：`AfterSaleQueryTool` 只加了四个只读字段
（`refundNo` / `refundAmountCents` / `refundAmountText` / `refundLabel`），
没有任何新增写工具。

## 4. 数据与事务

### 4.1 表结构

```sql
CREATE TABLE IF NOT EXISTS shop_aftersale_refund
(
    id           BIGINT      GENERATED BY DEFAULT AS IDENTITY,
    refund_no    VARCHAR(32) NOT NULL,
    return_id    BIGINT      NOT NULL,
    amount_cents BIGINT      NOT NULL,
    operator_id  VARCHAR(64) NOT NULL,
    created_at   TIMESTAMP   NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT pk_shop_aftersale_refund PRIMARY KEY (id),
    CONSTRAINT uk_shop_aftersale_refund_no UNIQUE (refund_no),
    CONSTRAINT uk_shop_aftersale_refund_return UNIQUE (return_id),
    CONSTRAINT fk_shop_aftersale_refund_return
        FOREIGN KEY (return_id) REFERENCES shop_aftersale_return (id),
    CONSTRAINT ck_shop_aftersale_refund_amount CHECK (amount_cents > 0)
);
```

为什么独立成表而不是给退货单加两列：

1. "最多一笔"用唯一键表达，比"两列必须同时为 null 或同时非 null"好写也好查；
2. 退款是**独立事实**，有自己的单号、操作人、时间；将来要支持部分退款 / 多次退款，
   只需放开唯一键、加一条汇总规则，不必动退货单主表；
3. 退货单主状态仍然只有三态（`SUBMITTED / APPROVED / REJECTED`）——
   退款不改状态，看 `refund` 字段有没有值就知道。

### 4.2 事务步骤

```
TX（@Transactional）:
  1. 预检（不加锁）：退货单存在 + 已批准
  2. 锁订单行 SELECT ... FOR UPDATE        ← 与 A1 新申请、B1 决策、B2 收货同一把锁
  3. 拿锁后重读退货单，再判一次已批准
  4. 拿锁后重读"这张单退过款没有"（uk(return_id) 兜底）
  5. 重读累计实收，必须 == 批准数量
  6. 单价一致性校验（退货单快照 vs 订单行成交价）
  7. 金额 = 成交单价 × 累计实收（整数分）
  8. 插入退款记录
COMMIT
```

锁顺序与 B2 完全一致（`shop_order_item` 行锁 → 退货单条件更新 → 额度条件更新 → insert），
所以"收货与退款同时发生"不会互相死锁：它们排在同一把锁上，串行通过。

## 5. B2 定向修复：最后一批收货的幂等边界

### 5.1 缺陷

`AfterSaleReceiptWriter` 拿锁后的顺序原本是**先判超收、再插收货记录**，
而幂等键只在事务外预检过。于是这条时序会误判：

```
请求 A、B 同键同参（同一批，receivedQty=1，批准数量正好 1）
A: 事务外预检 → 没记录
B: 事务外预检 → 没记录（A 还没提交）
A: 拿锁 → 累计实收 0，1+0 ≤ 1 → 插入 → 提交（累计实收 = 1）
B: 拿锁 → 累计实收 1，1+1 > 1 → 409 RECEIPT_OVER_APPROVED   ← 它其实只是一次重试
```

调用方看到 409，会以为"多收了"，而事实是"这一批已经成功了"。

### 5.2 修法（最小改动）

把"按 `request_key` 查同次操作是否已落库"插到"判状态 / 判可收数量"**之前**：

```java
AfterSaleReturn fresh = repository.findReturnByNo(returnNo).orElseThrow(...);

// 先确认"这一次操作是不是已经落库了"，再判还能收几件
Optional<StoredReceipt> existing = repository.findReceiptByRequestKey(requestKey);
if (existing.isPresent()) {
    return replay(existing.get(), requestHash);   // 命中 → 核对哈希 → 返回原记录
}

requireApproved(fresh);
int alreadyReceived = repository.sumReceivedQty(fresh.id());
if (alreadyReceived + receivedQty > fresh.quantity()) { ... 409 ... }
```

`replay(...)` 抽成 `static`，事务外预检与锁内回放共用同一份实现——
两处口径不会漂移（哈希不一致一律 409 `RECEIPT_REQUEST_CONFLICT`）。

语义因此变得干净：**"同一次操作的重试"回放原记录，"真的想多收"才 409**。

### 5.3 定向验收

| 场景 | 期望 | 覆盖用例 |
| --- | --- | --- |
| 同键同参并发，且这一批正好收满 | 两次都 201、指向**同一条**收货记录、只入库一次 | `AfterSaleReceiptPostgresTest#concurrentSameKeyWritesOnce` |
| 同键不同参 | 409 `RECEIPT_REQUEST_CONFLICT`，零写入 | `AfterSaleReceiptIntegrationTest` |
| 不同键争最后一件 | 一个 201、一个 409 `RECEIPT_OVER_APPROVED`，累计不超批准数量 | `AfterSaleReceiptPostgresTest#concurrentReceiptsCannotOverReceive` |

## 6. 旧库升级（不清库）

全部语句幂等，`spring.sql.init.mode=always` 每次启动都会跑一遍：

- 新表 `shop_aftersale_refund` 用 `CREATE TABLE IF NOT EXISTS`；
- 表与列的 `COMMENT` 用 `COMMENT ON ... IS ...`（PG 语义，H2 `MODE=PostgreSQL` 同样可用）；
- 不改任何既有列、不删任何既有数据。

`AfterSaleOldSchemaMigrationTest`（5 例）覆盖"旧库启动 → 建新表 → 老数据仍可读"。

## 11. 限制与未验证项

- **没有真实资金流**：不接支付平台、不生成对账文件、没有退款回执。页面文案严格停在"模拟退款"。
- **不支持部分退款 / 多次退款**：`uk(return_id)` 直接禁止第二笔；要支持需要先定汇总规则。
